## Семантика «Кейс N» в дизайне

Обнаружено: **`number` в data НЕ равен `id`** — это **намеренная дизайн-семантика**:

- `id=case1` → «Кейс 1»
- `id=case2` → «Кейс 1» (тот же!)
- `id=case3` → «Кейс 1»
- `id=case4` → «Кейс 2»
- `id=case5` → «Кейс 2»
- `id=case6` → «Кейс 3»
- `id=case7` → «Кейс 3»
- `id=case8` → «Кейс 3»
- `id=case9` → «Кейс 3»
- `id=case10` → «Кейс 4»
- `id=case11` → «Кейс 4»
- `id=case12` → «Кейс 5»

То есть у Екатерины **5 «дизайн-номеров»** для 12 кейсов в файлах. Codex сохранил это поведение 1-в-1 (без визуальной регрессии).

Если пользователь захочет унифицировать (id=N → «Кейс N») — поменять `number` в `app/data/portfolio.ts`.

## Lessons learned

- **Codex справился за 1 заход** с ТЗ на 11 шагов. Это успех — был риск 2-го захода.
- **Baseline HTML diff** — самый надёжный способ верификации визуальной регрессии без скриншотов. Текст/alt/число «Кейс» = инварианты.
- **Number ≠ id** — нелогично, но это дизайн-решение. Codex правильно интерпретировал.
- **3411 строк монолита** — это цена «без визуальной регрессии без макетов». Когда будет доступ к макетам — можно переписать.
